# ES3D reference implementation: architecture

The repository is a single dependency-free codebase of plain ES modules (Vite is the dev server and bundler; Playwright and three.js are development dependencies). The same modules run in the browser (the website, its converter and ES3D Studio) and in Node (tests, CLI, benchmark): nothing below `src/ui`, `src/modeller/app.js`, `docs/site` and `src/render` touches the DOM.

```
                ┌──────────────────────────── src/format ────────────────────────────┐
 .es3d text ──► │ xml-tokenizer → xml-parser ─┐                                      │
 compact     ──►│ compact-tokenizer → parser ─┼─► AST (ast.js) ─► validator ──► typed AST
 JSON        ──►│ json.js ────────────────────┘      ▲   (schema.js, values.js)       │
                │ serializer.js (encode) ◄───────────┘   errors.js: diagnostics      │
                └────────────────────────────────────────────────────────────────────┘
                                          │
              src/scene/scene-graph.js    ▼   SceneNode tree, materials, geometry descriptors
              src/scene/flatten.js        ▼   RenderScene: flat instance table (SoA)
              src/geometry/*  (lazy)      ▼   meshes per geometry and level of detail
              src/render/*                ▼   batches → instanced draws (WebGPU / WebGL2)
```

`src/pipeline.js` runs the first three stages (`compile()`); geometry is generated on demand.

## 1. Format layer (`src/format`)

**One AST for every syntax.** `ast.js` defines `Element`, `Attr`, `Comment` and `Document`. Attribute values stay strings in the AST and every node keeps its source offsets (name, value, open/close tags). This makes three things possible: exact diagnostics, lossless re-serialization (the editor and the inspector edit the *text*, not a regenerated document), and syntax conversion without loss.

- `xml-tokenizer.js` / `xml-parser.js`: a hand-written pull scanner for the XML subset; every token carries offsets. Structural errors (mismatched tags, unterminated strings) are fatal and located.
- `compact-tokenizer.js` / `compact-parser.js`: the LL(2) compact syntax (`group p=0,1,0 { sphere r=2 }`). It needs no schema: an element header ends at the first token that is not `NAME=`.
- `json.js`: JsonML conversion.
- `schema.js`: *the* table of elements, attributes, types, defaults, ranges, aliases and cross-attribute checks. The validator, serializer (aliases), inspector (widgets) and the generated [REFERENCE.md](REFERENCE.md) all read it.
- `values.js`: strict value parsers that throw `ValueError` with an offset *inside* the value, so a bad path command is underlined precisely.
- `validator.js`: walks the tree once: resolves aliases, parses every attribute into `element.values`, checks ranges, nesting and cross-attribute rules, registers ids, then resolves references (existence, kind, cycles). All problems are collected; suggestions come from `errors.js` (`suggest()`: edit distance plus prefix rules).
- `serializer.js`: markup/compact/JSON writers. *Pretty* output keeps the original spelling of each value; *minified* output re-formats typed values (shortest numbers, short aliases, minimal path data; float32 mesh data printed with the shortest digits that round-trip at float32 precision).

## 2. Scene layer (`src/scene`, `src/material`, `src/transform`)

`buildSceneGraph()` converts the validated AST into `SceneNode`s. Nodes are memoised per element, so a definition used by 10,000 `<use>` elements exists once; instancing is resolved by traversal, not by copying. Each node stores its static local matrix (`transform · T · R · S`), its style (material id / colour override), animations, and for shapes a geometry *descriptor* interned in the geometry cache.

`flattenScene()` walks the graph and writes a **RenderScene**: structure-of-arrays tables (`matrices` Float32Array, `geom`, `mat`, `uid`, `flags`, bounding `spheres`, LOD switch membership). `<repeat>` and `<scatter>` are expanded here with a reusable matrix stack and no per-instance allocation; where WebAssembly SIMD is available, the subtree below one copy is recorded once as a small program (`recordTemplate`) and the instance kernel runs it for every copy, giving the same rows bit for bit (see [wasm/README.md](../wasm/README.md)). Materials are resolved through `MaterialTable`, which deduplicates identical parameter sets. Animated subtrees are recorded as *dynamic segments*, so a frame re-flattens only the animated instances (`updateDynamic()`).

`picking.js` ray-casts against bounding spheres first, then the instance's mesh triangles, and returns the element uid the instance belongs to (for a `<use>`, the use element), which the UI maps back to source text. `raycast()` is the general form: a maximum distance, instance flags to skip, front faces only, and the world-space surface normal of the hit.

`animation.js` evaluates `<animate>`: a fraction from the clock (`dur`, `begin`, `repeat`) or from scroll progress (`timeline="scroll"`), eased, then turned into a value by from/to, by key values (linear or centripetal Catmull-Rom), or by an arc-length-parameterised path (`along`, flattened once with the sweep spine code). The flattener passes both time and progress, so `updateDynamic(scene, graph, time, progress)` re-evaluates either. `scene.animation` says which clocks a document uses, so viewers skip per-frame work for a scroll-only scene.

`camera-constraints.js` implements `<controls>` without the DOM: `applyLimits()` (distance, angle from straight up, target box) and `sweepCamera()`, which ray casts each camera move against front faces and stops it a near-plane-sized margin before the surface, sliding the rest of the move along it. Instances under `collide="false"` carry `FLAG_NO_COLLIDE` and are skipped.

## 3. Geometry layer (`src/geometry`, `src/path`)

- `registry.js` maps each shape element to a descriptor `{key, unit, lods, bounds, lodDeviation, generate(lod, quality)}`. The **key** identifies the geometry by value; the **unit** matrix moves size parameters into the instance transform, so every sphere in a document shares one canonical unit-sphere mesh (and every box one box mesh). Bounds are analytic, so culling works before anything is tessellated. `lodDeviation` is the chordal-error bound of each level.
- `geometry-cache.js` stores entries by key and generates meshes **lazily per level of detail**: a geometry that is never seen up close never gets its finest mesh. Entries survive document edits when their key is unchanged. It also keeps the diagnostics each level's generation reported, so that a mesh restored from the persistent cache (section 8) reports them again.
- `primitives.js` (box, rounded box, sphere, cylinder/cone, capsule, torus, plane, lines), `extrude.js` (caps, walls, quarter-round bevels with mitred insets), `revolve.js`, `sweep.js` (rotation-minimising frames, helix, Catmull-Rom spines, twist, taper), `gear.js` (involute profile), `mesh.js` (mesh builder, crease-angle normals, welding, edge/normal overlay lines).
- `src/path`: SVG path parsing with exact error offsets, adaptive flattening (tolerance relative to the path size and LOD), fill-rule region building (containment tree; walls only where the fill state changes) and ear-clipping triangulation with hole bridging and an area check that detects self-intersections instead of hiding them.

## 4. Renderer (`src/render`)

`createRenderer(canvas, {backend})` tries WebGPU and falls back to WebGL2. The facade (`renderer.js`) owns everything backend-independent; backends only upload buffers and issue draws.

Per frame:

1. **Camera** (`camera.js`): view/projection with automatic near/far from the scene bounds. The authored framing (`fov` at `aspect`) is fitted to the viewport by `fit` (`extentScale()`); the default applies `fov` to the shorter side.
2. **FrameBuilder** (`frame-builder.js`): evaluates `<lod>` switches, frustum-culls instance bounding spheres, and picks the coarsest automatic LOD whose chordal error projects to at most one CSS pixel (`options.lodPixels`), so every screen density chooses the same meshes. It then groups visible instances by *(geometry, LOD, material, mirrored)*. Every group becomes **one instanced draw**; instance matrices are written contiguously into one Float32Array.
3. **GeometryPool** (`geometry-pool.js`): all meshes, all LODs and all overlay line sets share **one interleaved vertex buffer and one 32-bit index buffer**, with indices stored pre-offset. A draw is just *(firstIndex, indexCount, firstInstance, instanceCount)*. There is no per-draw buffer binding, and new meshes are appended and uploaded incrementally. `setScene()` keeps the packed meshes (up to 32 MB), so a new document that shares meshes with the last one uploads only what is new; `renderer.prepare()` packs a view's meshes without drawing.
4. **Backends**: `webgpu-backend.js` (WGSL, bind groups per material, 4× MSAA, optional offscreen "readback" presentation for headless testing) and `webgl2-backend.js` (GLSL ES 3.0, per-material uniform buffers; WebGL2 lacks `firstInstance`, so instance attribute pointers are moved per batch). Mesh shaders are generated per material feature set and light setup (`shaders/glsl.js`, `shaders/wgsl.js`) and compiled on first use: a material samples only the textures it has, only alpha-masked materials can `discard`, the light loop is unrolled for the frame's light types, and untextured materials carry no texture coordinates. Both backends draw with 4× multisampling: WebGL2 asks for an antialiased canvas and draws straight into it when the browser grants at least 4 samples, and otherwise draws into its own 4× framebuffer and resolves it through a single-sample RGBA8 buffer into the canvas. Both pin the canvas colour space to sRGB and skip material and culling state that the previous batch already set. Shading is identical: metallic/roughness GGX with hemisphere ambient, up to 16 analytic lights, procedural or image textures, cotangent-frame normal mapping, ACES tone mapping and sRGB output. Mirrored instances flip the front-face winding.
5. **Overlays**: wireframe edges, normals and bounding boxes reuse the same pool and instance data (edges are deduplicated line lists generated once per mesh).

Statistics (`renderer.stats`) expose CPU frame time, draw calls, triangles, visible/culled instances, LOD histogram and upload/GPU byte counts; the Studio's statistics panel and the benchmark read them. `renderer.caps` reports what this device renders with (backend, MSAA samples, anisotropy, texture size limit, colour space, dropped lights).

Around the renderer:
- `stage.js` (`createStage()`) is what a web page embeds. It draws only when the camera, the animation time or progress, the size, the scene or a texture changed, and nothing while the canvas is off screen. It applies `<controls>` and drives scroll timelines. While the browser is idle it prepares the meshes for views sampled along the scroll path, and it reuses the previous document's geometry cache in `show()`. It reads a document's stored meshes before its first frame and stores new ones when the page is idle (section 8; `geometryStore: false` turns this off).
- `scroll-timeline.js` (`ScrollTimeline`) maps a page section's scroll position to progress, optionally pinned to `data-es3d-stop` elements. Scroll events only mark it stale; layout is read at most once per frame, and the value is eased.
- `orbit-controls.js` takes `configure(scene.controls)` and calls `constrainCamera()` after every drag, pinch and wheel step.

## 5. Conversion, optimisation and I/O (`src/io`, `src/optimize`)

- `obj.js`, `gltf.js`, `stl.js`, `step.js`: exporters write the *flattened* scene (OBJ, STL and STEP: every instance baked into world space, STL and STEP turned Z-up; glTF: one node per instance or `EXT_mesh_gpu_instancing`, optionally `KHR_mesh_quantization`). Importers turn OBJ (+MTL), STL (binary or ASCII, welded, normals from a crease angle), STEP (AP242 triangulated surfaces, planar faces, circles and cylinders; coordinates kept in the file's unit) and glTF (`.glb`, or `.gltf` with embedded or external buffers) back into a RenderScene, and `mesh-import.js` turns that into an ES3D document of `<mesh>` definitions and `<use>` instances (positions at a precision relative to the model size; normals stored or left to the reader's crease angle). A STEP file with a boundary representation does not take that mesh path. `step-brep.js` reads its exact geometry: every face's surface (plane, cylinder, cone, sphere, torus, linear extrusion, B-spline) and its loops of edges (lines, circles, ellipses, B-splines, with rational and degree-1 splines that are really circles or lines recognised as such), in the units the representation context names. `step-exact.js` writes each shell as one shape when it is one: a prism (two matching flat caps, straight walls) as a `<box>` or an `<extrude>` of the exact outline; a turned part (every face a full turn about one axis, or a flat ring across it) as a `<cylinder>`, a frustum or a `<revolve>` of the profile the faces make; a lone sphere or torus as that primitive. Otherwise each face becomes an element: a flat face a `<path>` (circular and elliptical arcs as `A`, polynomial splines as Bézier `Q`/`C` after knot insertion, holes as `evenodd` subpaths), and a face of revolution bounded only along its parallels and meridians a `<revolve>` of its meridian through the azimuth it spans. A face neither can describe (a B-spline surface, or a trim that is not a parallel or meridian) is tessellated from the exact surface: its loops are mapped to the surface's parameters (unwrapped across seams), the region is cut along a grid sized from the curvature, and each cell is triangulated and mapped back. A Z-up file is turned Y-up by a rotation on the outer group, so every coordinate is the file's own. The fixtures in `test/fixtures/step/` were made with OpenCascade, and the tests compare each conversion with that kernel's exact bounds and area. There is no boolean.
- `svg-import.js`: SVG drawings to *procedural* ES3D: SVG path data is ES3D path data, so every filled shape becomes an `<extrude>` of its outline and every stroke a tube (`<polyline d radius>`). Transforms are baked into the coordinates (arcs stay arcs under similarity transforms and become cubic Béziers otherwise); styles follow SVG's cascade (presentation attributes, simple `<style>` selectors, inline styles); `<use>`/`<symbol>` are expanded; gradients become their average colour.
- `convert.js`: the converter used by the website, the Studio's file loader and the CLI: `detectKind()` (magic bytes, then extension and content), `importFiles()` (main file plus companions such as `.mtl` and `.bin`, gzip transparently) and `exportFormat()` (every ES3D encoding, glTF, OBJ, STL, STEP).
- `optimizer.js`: semantic-preserving passes: strip defaults, deduplicate materials, detect linear patterns (consecutive siblings differing by a constant transform → `<repeat>`), extract repeated subtrees into `<defs>`/`<use>`, collapse redundant groups, weld meshes, minify paths, remove unused definitions. A token in an `x-` attribute that equals an existing id (an optional leading `#` is ignored) counts as a reference, and is updated when a duplicate material is merged, so an extension cannot lose the element it names. The inverse, `expandProcedural()`, writes every repeat/scatter copy explicitly (used by the benchmark to measure ES3D *without* procedural placement). Tests check that both produce the same rendered instance table.

## 6. Applications (`src/ui`, `src/modeller`, `docs/site`)

ES3D Studio (`docs/studio/index.html`, `src/ui/app.js`) wires the pieces together: a highlighted textarea editor with inline diagnostics, a scene tree, an inspector that edits attributes through minimal text edits (`text-edits.js`, so formatting and comments survive), a statistics panel with a format-size comparison, drag-and-drop/file loading (ES3D in any syntax, SVG, OBJ, STL, STEP, glTF, gzip), export to every format, orbit controls (with the document's `<controls>` limits when *Limits* is on, but always orbiting), a scroll-progress slider for scroll timelines, picking, and debug overlays. Compilation runs on a short debounce while typing. A document with errors leaves the last valid scene on screen and marks it stale.

The ES3D Modeller (`docs/modeller/index.html`, `src/modeller/`) is a separate application that writes ES3D and reads it back. It does not change the format. `model.js` holds the points, planes and paints and has no DOM, so the tests run it in Node. It decides whether a plane's points are flat, using Newell's normal and a tolerance of 10⁻⁶ of the model's size. It splits bent planes into triangles by ear clipping on the shorter diagonal, and it writes each plane as a `<polygon>`. Its `position` is the outline's lowest corner, and `rotation="pitch,yaw,0"` keeps the polygon's local x axis level and turns its local z axis outwards. The outline is measured in the frame of the rounded angles, so a reader rebuilds the corners to within 10⁻⁷ of the model's size. Every other element is an object (`objects.js`): its name, its attributes as written under their canonical names, its children and its text, so a file read in is written out with nothing lost. `placeElement` places a new element once from the picked points, given in the frame of the element it goes into. `checkModel` validates the document the model writes and returns the diagnostics per object, through the uids the validator records. The inspector (`inspector.js`) shows every attribute in the element's schema with a widget for its type. `fromES3D` keeps every element, walks plain groups with their transforms and inherited materials, turns their polygons into planes, and joins the corners that polygons share. `app.js` draws the model's ES3D plus editing aids (point spheres, edge tubes, a grid built with `<repeat>`) with `createStage`. Point handles are HTML on top of the canvas, so they can be clicked and dragged while the orbit controls keep the rest of the canvas.

The public site lives in `docs/`. Each page is a folder with `index.html` (`convert/`, `studio/`, `modeller/`, `examples/`, `spec/`, `reference/`, `media/`, `download/`, `faq/`), and the home page is `index.html`. `404.html` is shown for a missing address. Every page is listed in `docs/site/pages.js`, which gives the build its inputs and the site its `sitemap.xml` and link previews. They are styled by `docs/site/site.css`. Studio uses `docs/site/app.css`. `docs/site/vite-plugin-site.js` expands a few directives when Vite serves or builds a page: shared partials from `docs/site/partials/`, variables, the example gallery, and Markdown from `docs/` rendered by `docs/site/markdown.js`, so the site shows the same text as the repository. Every page built from the partials loads `docs/site/site.js`: the phone menu, and a tab stop on code blocks and tables while they scroll sideways. The home page shows the flat SVG logo first, loads the renderer once the logo is on screen and the page has loaded, then fades in the logo drawn live from the ES3D source printed on the same page (`docs/site/home.js`, `docs/site/viewer.js`). The converter (`docs/site/convert-page.js`) runs `src/io/convert.js` in the browser and hands the result to Studio through `localStorage` (`docs/site/handoff.js`). Studio's application code stays in `src/ui`.

## 8. Caching

Two layers, each with the web's own mechanism for what it holds.

**The document travels over HTTP and is cached by HTTP** (RFC 9111). An ES3D file is a few kilobytes of text, so the usual rules for text apply: serve it compressed (brotli or gzip, `Vary: Accept-Encoding`), with a strong `ETag`, and either `Cache-Control: no-cache` (revalidate, `304 Not Modified` when unchanged) for a URL whose content can change, or `Cache-Control: public, max-age=31536000, immutable` for a URL that carries a content hash. The reader adds nothing of its own here; `fetch()` and the browser's HTTP cache do it. Until `model/vnd.es3d` is registered (SPEC section 17), `text/plain; charset=utf-8` is the media type. The LAN benchmark server does all of this for its files (`benchmark/lib/http-cache.mjs`).

**The meshes are derived data and are cached by the reader** (`src/cache/`). Tessellating is the part of a load that glTF does not have, and it gives the same result every time, so a repeat visit can read it back:

- `geometry-store.js` keeps one record per document: the generated levels of every shape, in ES3D's own binary layout (`mesh-bundle.js`: a JSON description, then float32 positions, normals and uvs and 16- or 32-bit indices, read back as views without copying).
- The record is named by content: one SHA-256 (Web Crypto, or `sha256.js` where a page served over plain http has no `crypto.subtle`) over every shape's identity, the `GEOMETRY_REVISION`, the quality setting and what the engine's `Math` functions return for fixed arguments. A shape's identity is its key with the full text of every input the key hashes (`registry.js`), so two shapes whose short keys collide can never share a record. Nothing expires by date: if anything that shapes a mesh changes, so does the name. Authored `<mesh>` data is not cached; hashing it would cost as much as computing its normals.
- Records live in IndexedDB, which pages on plain http have too (Cache Storage does not exist there). The store keeps at most 64 MB and 256 records by default, least recently used first, records of another revision before anything else. `navigator.storage.persist()` is only asked for when the page passes `persist: true`.
- The cache is advisory and cannot change what is drawn. A missing, slow (over 250 ms), damaged or foreign record means the meshes are generated as before; restored meshes are bit-identical to generated ones; `test/geometry-cache.test.mjs` checks that for every example and benchmark scene, and fails when any generator's output changes without `GEOMETRY_REVISION` changing.
- `restoreGeometry()` runs after `compile()` and before the first frame (the stage, the site viewer and the Studio wait at most 50 ms for it); `saveGeometry()` runs when the page is idle (`persistGeometry()` debounces it). What is stored is what the page generated: with automatic LOD that is usually the coarser levels a view needed, not every finest mesh.

## 9. Design decisions worth knowing

- **Analytic bounds before geometry.** Every descriptor knows its bounds without tessellating, which is what makes lazy generation and per-instance LOD possible.
- **Canonical meshes + unit transforms** turn "many spheres of different sizes" into "one sphere mesh, many instances", which is both the main memory saving and the reason batching works so well.
- **Deterministic procedural placement** (`<scatter>` with a specified PRNG) is what lets a 600-byte file describe 7,000 positioned objects; it is also a compatibility burden every reader has to implement bit-exactly.
- **No silent repair.** Invalid values are errors, degenerate outlines are warnings that say what was dropped, and partial triangulations report the covered area.
- **Load speed is engine work.** Generators count their vertices first and fill arrays of the exact size, hot loops run over flat typed arrays rather than small vectors, and the short-lived classes of the reader (mesh builder, scene walker, tokenizer, triangulation node) each keep one instance alive, so a full garbage collection does not make the engine throw away the optimised code that uses them. None of this may change the output: a faster generator produces the same bits.
- **WebAssembly for the hottest loops, JavaScript as the reference.** Number lists, crease normals, sweeps, triangulation, extrusion walls, primitives, the sphere bound and the instance rows of `<repeat>` and `<scatter>` also exist as C kernels (`wasm/`, embedded in `src/wasm/kernels-binary.js`; the instance kernel uses SIMD and is a module of its own). They give the same bits as the JavaScript versions, which remain the fallback where WebAssembly is unavailable; see [wasm/README.md](../wasm/README.md).
- **One renderer for all formats, and a reference engine beside it.** OBJ and glTF imports produce the same RenderScene type, so most benchmark rows compare formats, not renderers. The device benchmark also loads the same GLB with three.js (GLTFLoader and its renderer) and hands ES3D to three.js (`src/bench/three-engine.js`), so ES3D is compared with glTF as pages actually show it, and format and engine can be told apart.
